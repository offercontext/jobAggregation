## 1. 已观察到的原因

`api.py::upload_resume` 仅调用 `_extract_pdf_text`，把全文写入 `parsed_data` 和 `content_json.raw_text`，状态为 `text-ready`。`structuredResume.ts` 将不存在的结构化模块解码为空；`ResumeEditorDrawer.tsx` 将 `rawText` 放进“其他”。因此上传成功不等于结构化完成。

## 2. 方案选择

- 只改标签：可避免误导，但不能填充模块，不足以修复。
- 标题/正则分段：对固定模板便宜，但双栏 PDF、同义标题和混排容易分错，不能作为通用成功路径。
- **采用 AI 结构化候选 + 用户核对保存**：复用现有 Non-Agent JSON 调用边界，生成候选而非直接改简历。失败保留提取原文，明确告知未完成分类。

不新增 OCR、简历润色、经历补全、自动确认事实、Agent 工具或自动迁移历史简历。

## 3. 用户流程

新上传：PDF 保存和文本提取成功后，显示“已提取文字，待分类”，提供“AI 分类并核对”。按钮旁明确说明简历文字会发送给当前配置的 AI；用户点击才启动调用。上传本身不自动增加 AI 成本。

已有上传简历：同样提供“重新解析并核对”，无需重新上传。优先用保存的提取原文；缺少文本时提示重新提取/上传，不用其他简历作为替代来源。

解析中：按钮防重复，保留页面及原内容。关闭或切换简历后，迟到结果不得套入其他简历或再次触发调用。

结果：按求职意向、基本信息、教育、工作（含实习）、项目、技能展示候选和对应原文片段，允许修改、取消。无法识别的内容留在原文，不强行猜测分类。

保存：用户点击“确认填入空白模块”后才持久化；成功回读并刷新完整度。取消、解析失败、超时不修改正式简历。历史记录不自动批量重解析。

## 4. 数据与合并边界

沿用 `career_intent/contact/education/experience/projects/skills` 当前字段结构。提取原文继续保留在 `raw_text`，上传简历的页面将其呈现为独立只读“PDF 提取原文”，不再挂在“其他”。新增的手工补充文本使用独立字段，不覆盖原文；其他来源的简历保持现有编辑能力。

AI 输出使用封闭、限长 Schema；数组项与字符串有上限，拒绝非法 JSON、额外未知操作字段及超限结果。仅允许从此次原文提取事实，不能推断姓名、学历、时间、量化成果或求职意向；每个候选值附可定位的原文支持。可验证原文片段存在不等于事实已经认证，全部结果仍标记“待核对”。

合并规则：默认只补空白；已有非空标量不替换；已有非空经历/项目/技能数组不追加、不重排、不整体覆盖；未知旧字段原样保留。冲突字段留作参考，不提供含糊的“一键覆盖全部”。用户仍可在原编辑器中主动修改已存在内容。

预览绑定 resume ID 与服务端返回的内容版本指纹。指纹覆盖当前 `content_json`、提取文本及相关解析状态；仅在私有请求/响应中使用，不写普通日志。最终保存必须在同一数据库写事务内重新加载、检查可见性/未删除与版本一致后执行合并。不同则409并要求重新核对，不能仅靠前端比对。禁止把 Provider 调用放入该事务。

确认成功仅表示用户接受分类，不改 source/is_master/parent_resume_id，不自动升级来源可信级别，不生成事实补充审批、Story、Practice、Pending 或 Ledger Operation。既有手工简历编辑路径不改成 AI 工具写入。

## 5. API 和 Provider 边界

保持 `/api/resumes/upload` 的 PDF 上传和原文件保存行为。新增独立的结构化预览 POST 及确认保存 POST，分别承担只读生成与用户确认合并；原 PATCH 保持兼容，不让新流程绕过并发校验。

预览：只读加载指定简历，校验可见性、原文非空及输入上限，冻结数据后调用既有 `ai/workflows.py::complete_json` 边界；业务校验和严格解码在独立简历解析模块。不得导入新 Provider SDK、改 Tool Catalog 或偷增 Agent 调用点。沿用当前 AI 配置与 Non-Agent 客户端的既有行为，不额外增加 JSON 修复调用或自动重试循环；记录逻辑生成调用计数，并测试底层原有 fallback 行为不被额外扩大。

AI 未配置、网络/Provider 失败、超时、输入超限、结果非法分别使用稳定的用户提示，不返回原始异常、密钥或完整模型结果作为错误文本。失败不是“已解析”。取消及其他 BaseException 沿用现有取消契约，不转成成功候选。

输入上限为 UTF-8 128 KiB，同时服从配置的模型窗口和输出预留；不可静默截断全文后声称完整解析。候选总 JSON 上限128 KiB，单字符串8 KiB，每类数组最多100项，超限返回明确失败。原PDF提取与上传10MiB限制保持现状。

确认保存：校验有限大小的候选、原文支持与用户核对的字段结构，基于新鲜数据只填空白并做原子版本检查；所有检查通过后单事务写入。客户端返回的“可信”“已认证”等字段不接受。不要为了完成本修复把候选结果升级为权威事实。

## 6. 状态显示

- 原文存在但未结构化：已提取文字，待分类。
- 当前请求运行中：正在分类（瞬态）。
- 候选已返回：分类完成，待核对（瞬态，未保存）。
- 确认已保存：已核对分类；内容完整度继续由真实字段计算，不能等同于简历完整。
- 无提取文字：未提取到文字；本期不支持扫描件OCR。
- 解析失败：原文已保留，分类未完成，可主动重试。

优先用现有内容与兼容元数据表达上述状态，不重建数据库表；不能仅凭 `text-ready` 显示“结构化完成”。新增持久状态或元数据必须在实施时逐一检查现有消费者，不修改其他AI工作流的来源判定。
